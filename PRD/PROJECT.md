## 0. Назначение этого файла

Этот файл определяет **как именно ведётся разработка Vimana**. Это точка входа в проект, инструкция по чтению PRD-системы, правила выполнения задач и контракт между стратегией, дизайном и реализацией.

Любой исполнитель — человек или AI — **обязан начать работу с этого файла**.

PROJECT.md управляет **процессом**, но не переопределяет **смысл**. Смысл задаёт MASTERPLAN.

При конфликте побеждает **старший**:

1. **MASTERPLAN.md** — высший уровень истины

`PROJECT.md` не переопределяет смысл, а управляет процессом.

## 4. Два потока (главный механизм)

- **PLANNING** — поток проектирования. Запускается в начале проекта, идёт строго **старший → младший** (от MASTERPLAN к TASKS). Каждый младший файл обязан соответствовать всем старшим над ним. Не хватает основания для младшего — поднимись к старшему и сначала исправь там.
- **UPDATES** — главный рабочий поток во время исполнения. Изменение фиксируется на **самом младшем уровне, где оно корректно живёт** (обычно TASKS) и поднимается к старшему **ровно настолько, насколько изменение этого требует** (правило минимального подъёма).

Подъём до MASTERPLAN — редчайшее событие. Правка PROJECT (корня) — чрезвычайное событие, затрагивает весь фундамент; избегать максимально.

**Кто имеет право писать:** задачи и их статусы — любой исполнитель (человек/AI). Подъём к DESIGN/USERJOURNEY/IMPLEMENTATIONPLAN — с явным описанием причины. Подъём к MASTERPLAN/PROJECT — только человек-владелец продукта.

## 5. Правила работы с TASKS.md

- TASKS.md — **единственный исполняемый файл.** Если задачи нет в TASKS — её **не существует**.
- Задачи выполняются **строго по порядку** (сверху вниз). Нельзя перескакивать фазы из IMPLEMENTATIONPLAN.
- Любая работа начинается с задачи и заканчивается обновлением её статуса.

После выполнения задачи исполнитель **обязан**:

### 6.1 Capture Discovered Logic (обязательно)
Разобравшись в том, как работает блок системы, исполнитель **обязан**: проверить, описано ли это в `TECHSTATE.md`; если нет — добавить краткое описание логики с **указанием файлов реализации**. Делается **до** завершения задачи.

### 6.2 Task Closure Checklist (обязательный, блокирующий)

Задача считается закрытой **только когда все пять пунктов сделаны в одном сеансе**. Пропуск любого пункта = задача открыта, даже если код запушен.

- [ ] **TASKS.md** — пункт помечен ✅ (либо на строке `### T<X>`, либо на **Acceptance**, обычно оба).
- [ ] **TECHSTATE.md §1 Status** — соответствующая строка `⬜ не начато` → `🟨 в работе` → `✅ готово (T<X>)`.
- [ ] **TECHSTATE.md §3 «Обнаруженная логика»** — новые модули/файлы добавлены в таблицу «Механика → файлы реализации».
- [ ] **CHANGELOG.md** — новая запись сверху, уровень `MILESTONE` (для завершения задачи), формат `YYYY-MM-DD · MILESTONE · T<X> …`. Одна запись на задачу, даже если работа в несколько коммитов.
- [ ] **frontend/src/version.ts** — проверить, что версия соответствует текущей фазе по правилу `0.<фаза:02>.<часть фазы>` (см. CLAUDE.md). Меняется при переходе на новую фазу или её часть, **не после каждой задачи** — внутри одной фазы обычно остаётся прежней.

- [ ] **Новые функции объявлены** по §6.2a — имя, строка о назначении, кто вызывает. Функция без вызывающего названа вслух и записана в **TECHSTATE §3a**.

Дополнительно, если применимо:
- Новые модели → **TECHSTATE §4** обновлён.
- Новые env-переменные → **ENVIRONMENT.md §3** дополнен.
- Новые Decision → **TECHSTATE §2** Decision Log.

**Правило minimum-effort**: если задача была маленькой (правка типа fix) — CHANGELOG уровня `FIX` вместо `MILESTONE`, остальные пункты остаются обязательными.

### 6.2a Объявление новых функций (обязательно)

*Добавлено 2026-08-08 по прямому указанию владельца — правка корня, см. §8.*

Каждая **новая функция, метод или модуль**, появившиеся в задаче, объявляются в отчёте о задаче: **имя, одна строка о том, что делает, и кто её вызывает.** Последнее — главное.

```
+ core/verification.issue_code(user, channel) — выдаёт 6-значный код, кладёт хеш в БД.
  Вызывает: api/auth.request_code
+ core/verification._normalize(value) — приватный, E.164 через phonenumbers.
  Вызывает: issue_code, verify_code
```

**Зачем именно «кто вызывает».** Функция без вызывающего не проверена ни одним тестом и не исполнялась ни разу, но выглядит рабочей — и следующий исполнитель обопрётся на неё как на готовое. Ревизия 2026-08-08 нашла семь таких в `backend/app`, два модуля во фронте и двадцать осиротевших i18n-ключей; все они пережили по несколько задач молча. Отдельно показателен `logger` в `tasks/notifications.py`: его не было **вовсе**, три админских таска звали его в фолбэке, и ветка падала ровно тогда, когда была нужна. Строка «кто вызывает» ловит это в момент написания, а не через полгода grep'ом.

Функция, у которой на момент закрытия задачи вызывающего **нет**, — это не ошибка сама по себе, но она обязана быть названа вслух и попасть в **TECHSTATE §3a** с причиной, по которой оставлена. Молча оставленный хвост — нарушение правила, даже если код верен.

### 6.2b Гигиена сервера при закрытии этапа (обязательно)

Выполняется **один раз на закрытие фазы**, не на каждую задачу. Сервер — `t3.small`: 2 ГБ памяти, 28 ГБ диска. Каждая пересборка оставляет слой кэша, за две недели набегает ~3 ГБ.

```bash
df -h / && docker system df
docker builder prune -f --filter until=168h
docker image prune -f
docker container prune -f
df -h /
```

Что делает каждая команда и почему именно она:

- `builder prune --filter until=168h` — кэш сборки старше недели. Свежий оставляем: без него следующая сборка тянет `pip install` и `npm ci` заново, это минуты.
- `image prune` (**без `-a`**) — только dangling-образы, потерявшие тег после пересборки. С `-a` удалились бы и рабочие образы, включая те, на которые можно откатиться.
- `container prune` — остановленные контейнеры.

Тома — отдельно, **со взглядом на список перед удалением**:

```bash
docker volume ls
```

Анонимные (длинные хеши) остаются от удалённых контейнеров и чистятся смело. Именованные — `vimana_postgres_data`, `vimana_nostr_whitelist` — это вся база и история relay'я, восстановления нет. `docker volume prune` удаляет только не привязанные ни к одному контейнеру, то есть рабочие не тронет; но запускать его, не посмотрев список, не стоит — цена ошибки необратимая, а взгляд стоит десять секунд.

```bash
docker volume prune -f     # только после `docker volume ls`
```

**Никогда не запускать на этом сервере:** `docker system prune -a` — сносит все неиспользуемые образы разом, включая предыдущую версию, на которую откатываются при плохом деплое.

Заодно, раз в фазу:

```bash
free -h                          # swap подключён? (2 ГБ, добавлен 2026-07-30)
docker ps --format '{{.Names}}\t{{.Status}}'
```

Смотреть на `(unhealthy)` и `Restarting`. Оба состояния умеют держаться неделями молча: healthcheck фронтенда врал 11 дней, `mcp-server` столько же перезапускался по кругу — и ни то ни другое не всплыло бы само.

**Why:** 2026-07-30 полный прогон тестов трижды убил OOM-killer. Причин было две — отсутствие swap и пять подвешенных `Ctrl+Z` заданий, продолжавших работать внутри контейнера. Диск при этом был занят на 23%, из них 3 ГБ — кэш сборки. Ни одно из трёх не заметно, пока не упрётся.

**Чего оптимизировать НЕ надо (замерено 2026-07-30).** В покое все семь контейнеров держат ~374 МБ из 1.9 ГБ: backend 260, db 58, celery-worker 32, остальные по единицам. Полтора гигабайта свободны, один прогон `pytest` берёт ~540 МБ и помещается с запасом. Машина не мала — OOM случался только когда прогонов было несколько разом. Отсюда единственное действующее правило: **не запускать прогоны параллельно** и помнить, что `Ctrl+Z` не отменяет `docker compose exec`, а подвешивает клиента, оставляя процесс внутри контейнера живым. Подкручивать healthcheck-интервалы, лимиты Postgres и прочее смысла нет: выигрыш в доли процента, риск сломать порядок запуска через `condition: service_healthy` — реальный.

### 6.3 Обязательный `git diff` перед коммитом (AI-агенту)

При работе агента через инструменты редактирования (`Edit`, `Write`) с несколькими файлами в одной итерации **некоторые вызовы могут молча упасть** (stale file-state cache, конфликт с параллельной операцией) — сообщение об успехе не гарантирует что изменения применились ко ВСЕМ файлам.

**Правило перед `git add` / `git commit`:**

1. Выполнить `git status --short` — увидеть какие файлы реально изменились.
2. Сравнить с ожидаемым списком (все файлы, к которым были обращения `Edit`/`Write`). Если файл ожидался, но не в diff — Edit упал молча.
3. Для критичных изменений (route в App.tsx, миграция alembic, security header в nginx) — дополнительно `git diff --stat <file>` перед push, убедиться что число вставок > 0.
4. Если после push тесты (backend pytest / Playwright) выявляют «пустоту» на роуте или отсутствие поля — **сначала проверить `git log -p <file>`** реально ли этот код в HEAD, только потом смотреть runtime.

**Why это правило:** 2026-07-18 при T3.3 (Recipient role) `Edit` к App.tsx с добавлением `<Route path="/join/deal/:token">` молча упал. Frontend компилировался (import не был обязателен для сборки), backend отдавал 200 на XHR, но React Router не находил match → белый экран. Обнаружено только через T_TEST.3 Playwright smoke спустя два коммита. Правило добавлено чтобы не терять время на runtime-детектив когда причина в git-состоянии.

**Как проверить дёшево:** `git diff HEAD --stat` перед `git add` — 3 секунды, покрывает 95% случаев.

### 6.4 Ротация `TASKS.md` и `CHANGELOG.md` (по границам этапов)

Эти два файла — журналы, они растут монотонно. Без ротации через 3–6 месяцев работы каждый обгонит 300 KB и подгружаемый контекст съест значимую долю бюджета токенов при каждом чтении/редактировании. Правила ниже — обязательные.

**Главный принцип: ротация идёт по границам этапов, а не по размеру.** Размер — индикатор, а не команда. Приоритет — целостность и читаемость для агента: этап должен читаться одним куском, из одного файла, без прыжков между активным и архивом. Файл, переваливший ориентир по размеру, — не проблема; **разорванный посреди этапа файл — проблема.**

#### Именование архивов

- **Активный:** `PRD/TASKS.md`, `PRD/CHANGELOG.md`.
- **Архивы:** `PRD/TASKS_ARCHIVE_01.md`, `_02.md`, ... (нумерация двузначная, инкрементальная). Аналогично для CHANGELOG.
- Каждый архив содержит **целое число завершённых этапов** — непрерывный диапазон, никогда не половину этапа и не выборку по темам.

#### Триггер ротации

**Ротация возможна только на границе этапа.** Внутри этапа не режем никогда, каким бы ни был размер.

Порядок:

1. Этап (`## ЭТАП N` / фаза) завершён — все его задачи закрыты.
2. В этот момент замерить размер:
   ```bash
   wc -c PRD/TASKS.md PRD/CHANGELOG.md
   ```
3. Если активный файл **превысил ориентир ~100 KB** — завершившийся этап **дописывается в текущем файле до конца**, а **лог следующего этапа начинается в новом активном файле**; текущий целиком становится архивом.
4. Если ориентир не превышен — следующий этап продолжается в том же файле.

Ориентир 100 KB не обязывает резать немедленно и не запрещает превышение: он лишь отвечает на вопрос «начинать ли следующий этап с чистого файла». Cross-cutting задачи (`T_SEC.*`, `T_UX.*`, `T_TEST.*`, `T_AGENT.*`, `EXP-*`) идут сквозь этапы и **границы не образуют** — они переезжают вместе с ближайшей ротацией по фазе.

#### Что в новом активном файле после ротации

**`TASKS.md` active** — начинается с чистого листа для следующего этапа:
- Все `[ ]` open задачи + их полный контекст.
- Заголовки фаз (`## 📦 ЭТАП …`) — навигационная структура.
- **Одно-строчные стабы** для закрытых задач, на которые ссылаются open (сохранение зависимостей):
  ```
  ### T2.1 — Peer Identity Verification ✅ MVP (archived → TASKS_ARCHIVE_01.md#T21)
  ```
  Стаб пишется если хотя бы одна open задача упоминает `T_X` по номеру в описании/acceptance.
- Индекс архивов сверху — **с указанием этапов**, не только дат:
  ```
  > Архивы закрытых задач:
  > - TASKS_ARCHIVE_01.md — ЭТАПЫ 0–3.5, T0.1 … T3.5 pt.2 (2026-06 … 2026-07-18)
  ```

**`CHANGELOG.md` active:**
- Записи текущего (незавершённого) этапа. **Записи одного этапа не разделяются между файлами** — критерий по количеству записей или по календарным месяцам не применяется.
- Индекс архивов сверху с этапами и диапазоном дат.

#### Что уходит в архив

- **Все** блоки завершённого этапа целиком, в оригинальном виде: описание, acceptance, checklist ✅, follow-up.
- Все MILESTONE-записи CHANGELOG этого этапа целиком.
- Незакрытые задачи завершённого этапа **не архивируются** — переезжают в новый активный файл вместе с открытым бэклогом.

#### Правило зависимостей (без orphan'ов)

**Проверка перед перемещением задачи `T_X` в архив:**
```bash
grep -n "T_X\|T${X}" PRD/TASKS.md | grep -v "^### T${X}"
```
Если grep возвращает строки в других задачах — оставить одно-строчный стаб в активном файле. Если нет — полный move в архив.

Аналогично для CHANGELOG: если новая запись ссылается на старую (`см. запись от …`), проверить что старая ещё в active, иначе переформулировать ссылку.

#### Правило редактуры новых записей (снижение bloat)

- **CHANGELOG MILESTONE-запись ≤ 500 символов.** Все детали (файлы реализации, decision'ы, imports) → в TECHSTATE §3 и TASKS acceptance. CHANGELOG остаётся «что и когда закрыто», не «как построено».
- **TASKS closed запись** должна сохранить: номер, название, статус ✅, одно-строчный acceptance, ссылка на CHANGELOG-запись. Всё длиннее — оптимизировать в момент закрытия задачи, не архивировать.

#### Как выполнять ротацию (пошаговая инструкция агенту)

0. **Убедиться, что этап действительно завершён.** Если хоть одна задача этапа открыта — ротации нет, независимо от размера. Это условие проверяется первым и отменяет все остальные.
1. `wc -c PRD/TASKS.md PRD/CHANGELOG.md` — превышен ли ориентир ~100 KB. Не превышен → следующий этап продолжается в том же файле, ротация не нужна.
2. `ls PRD/TASKS_ARCHIVE_*.md` — найти следующий номер (например `_02` если есть `_01`).
3. Создать `PRD/TASKS_ARCHIVE_NN.md` с заголовком-диапазоном **этапов** и дат.
4. Перенести в архив **весь завершённый этап целиком**, в оригинальном виде. Ничего не сокращать и не переписывать при переносе — архив хранит блоки такими, какими они были закрыты.
5. В новом активном оставить: open-бэклог, заголовки фаз, стабы для закрытых задач с зависимостями (проверка — ниже).
6. Обновить индекс архивов сверху активного файла.
7. Аналогично для CHANGELOG: границей служит тот же этап, не календарь.
8. Commit: `prd rotate tasks/changelog N` — важен маркер `rotate` чтобы историю ротаций легко находить в `git log --grep=rotate`.

**Чего не делать:** не резать посреди этапа ради размера; не разносить блоки одной задачи по двум файлам; не сокращать содержимое при переносе. Экономия килобайт не стоит того, чтобы агент читал историю одного этапа из двух мест.

## 7. Тестирование как обязательный шаг

Ни одна задача не завершена без проверки:

- **Business Logic Integrity** — учтены ли краевые случаи?
- **Security Integrity** — безопасны ли данные, ключи и средства пользователей?
- **System Integrity** — не нарушена ли архитектурная логика?

Не пройден тест — задача возвращается в работу.

### 7.1 Testing Pyramid — стратегия

Тесты расширяются послойно снизу вверх по частоте прогона и стоимости поддержки:

```
                 ▲
                / \
               /   \
              / VR  \     Visual regression, Chaos
             /-------\    (редко, ручная триаж)
            /  E2E    \
           /   full    \   Multi-context Playwright, full business flows
          /-------------\
         / Contract/Load \  schemathesis, k6, ZAP scan
        /-----------------\
       /   Smoke E2E       \  Playwright happy-path (T_TEST.3)
      /---------------------\
     /    Integration        \  pytest + TestClient (backend), vitest
    /-------------------------\
   /         Unit              \  pytest pure funcs, vitest hooks (базис)
  /---------------------------- \
```

Правило: **новый layer активируется только когда нижний стабилен**. Не имеет смысла делать chaos-тесты пока unit падают.

### 7.3 Definition of Done по типам

| Тип | «Готово» = |
|---|---|
| **Unit** | branch coverage ≥ 80% для новой функции, оба true/false пути покрыты |
| **Integration** | endpoint + happy path + minimum 2 негативных кейса (auth, validation) |
| **Smoke E2E** | 3 спека проходят на prod за < 30 сек, `git push` → green |
| **Full E2E** | golden path сделки, verification 3-tier, dispute + arbiter reveal, threshold e2e |
| **Property-based** | invariants на всю крипту (SSS split→combine roundtrip), формулы (УБА clamp), BFS (depth limit) |
| **Contract** | OpenAPI spec = frontend types, автомат в CI |
| **Load** | 100 concurrent users на match/publish/chat без ошибок за 5 мин |
| **Security scan** | ZAP baseline `-r report.html` = 0 High, ≤ 3 Medium (документированные) |
| **Accessibility** | axe-core no violations на 5 главных страницах |
| **Visual regression** | опорные снимки для 10 канонических экранов, diff < 0.5% |
| **Mutation** | mutmut kill-rate ≥ 60% на критичных модулях (crypto, permissions, uba) |
| **Chaos** | сервис выдерживает 30-сек отключение Postgres/Redis без потери данных |

### 7.4 Progression schedule

- **Сейчас (Ф.3.5 done):** активны Unit + Integration + Smoke E2E. ~272 теста.
- **Активировать в Ф.3.5.х:** `T_TEST.5` Hypothesis (T2.3 SSS, T3.1 УБА, T2.4 BFS). Быстрая работа, огромный ROI.
- **Активировать перед Ф.4:** `T_TEST.4` (contract + fuzzing) + `T_TEST.6` (load-tests) + `T_TEST.7` (ZAP baseline). Перед платежами обязательно.
- **Активировать в Ф.4:** `T_TEST.3 pt.2` (full E2E multi-context), `T_TEST.8` (a11y).

**Правило-guardrail:** каждая новая задача-фича должна оставить coverage matrix не хуже чем было. Если добавили новый endpoint — новый integration тест обязателен. Если новая крипто-функция — property-based invariant.

## 9. Режим AI-агента и режим человека

**AI:** читает все PRD перед началом; выполняет только следующую валидную задачу из TASKS; не импровизирует вне TASKS; отчитывается после каждого шага; указывает сомнения и риски. AI — **исполнитель и партнёр, не автор стратегии**.

**Человек:** следует тем же правилам; может предлагать изменения, но обязан фиксировать их в системе файлов.

## 10. Финальный Integrity Check (перед релизом и после крупных изменений)

1. **В сохранности ли записи?** DealVault иммутабелен — записи/фото нельзя удалить или подменить?
2. **Не держим средства?** Платформа хранит **только ключ арбитра**, а не средства пользователей?
3. **Прозрачность.** Понятно ли сторонам, что разрешено к перевозке и кто несёт риск?
4. **Идентификация ролей.** Видно ли, кто Отправитель / Перевозчик / Получатель / Оператор?
5. **Комплаенс.** Есть ли подтверждение о запрещёнке, пройдена ли **peer-верификация** (Фаза 2, T2.1) для передачи ценного и **regulatory KYC** (Фаза 4, T4.1) там, где он обязателен для платежей? **Информирован ли пользователь через `RouteNote` о специфике коридора** (T_UX.2, D-COMPLIANCE-STANCE) — платформа не блокирует направления, только показывает известные особенности.
6. **Не-курьер.** Ясно ли, что Vimana — информационный и эскроу-слой, а не перевозчик?

Если хотя бы одно «нет» — вернуться к MASTERPLAN.md.
