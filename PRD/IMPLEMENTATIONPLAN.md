## 1. Роль документа

Отвечает на вопрос: **в каком порядке мы строим Vimana, чтобы каждая фаза была готовым MVP, а архитектура выдерживала рост?** Всё в итоге питает `TASKS.md`. Фазы идут через **функциональные блоки**: от самого простого и важного к более сложному.

## 2. Базовые принципы

### Продуктовые
- **Trust-first.** Иммутабельность записей доставки (DealVault) — append-only, фото нельзя удалить/подменить.
- **Non-custodial-first.** Платформа никогда не держит средства пользователей — только ключ арбитра. Архитектура эскроу проектируется под это с самого начала.
- **Platform-not-carrier.** Vimana — информационный и эскроу-слой; риск перевозки несёт пользователь.

### Инженерные
- **Сначала ядро данных, потом UI.** Если БД не связывает рейсы, заявки и стороны — UI бесполезен.
- **Event Sourcing Lite.** Любое изменение статуса сделки — отдельное неизменяемое событие (`DealEvent`).
- **Design for portability.** Данные проектируются как сериализуемые, отвязываемые от платформы объекты с Фазы 1 — чтобы в Фазе 4 включить экспорт и Nostr + IPFS без переделок моделей.
- **Миграции обязательны** (Alembic). Никаких ручных правок схемы.

## 4. Фаза 1 — Ядро доверия (V1)

> **Цель:** рабочий маркетплейс ручной авиадоставки + иммутабельная запись. Без денег на платформе, без эскроу.

⚠️ Нарушение порядка шагов внутри фазы ведёт к хаосу в БД и переделкам.

### 1.1 Модели данных (фундамент)
1. `User` — id, email/phone, password_hash, display_name, is_carrier, nostr_pubkey (nullable-заглушка, Фаза 2), business_activity_level (заглушка-поле), created_at.
2. `Connection` — id, user_id, connected_user_id, invite_token, created_at. Двусторонняя связь (запись для каждой стороны).
3. `InviteLink` — id, creator_id, token, expires_at, used_by (nullable). Одноразовая ссылка-приглашение.
4. `Trip` — id, carrier_id, origin, destination, depart_at, capacity, allowed_categories, status [draft, open, matched, completed, cancelled].
5. `Order` — id, sender_id, recipient_contact, origin, destination, category (enum: document, medicine, electronics, gift, other), declared_value, currency, description, deadline, status, trip_id (nullable).
6. `Deal` — id, order_id, trip_id, sender_id, carrier_id, recipient_id (nullable), status [draft, matched, accepted, in_transit, delivered, confirmed, closed, disputed], created_at.
7. `DealEvent` — id, deal_id, event_type [created, matched, accepted, handoff, in_transit, received, confirmed, closed], payload (JSON), actor_id, timestamp. **Append-only.**
8. `DealVaultMessage` — id, deal_id, sender_id, text, is_system, created_at. **Нельзя удалять/редактировать.**
9. `Attachment` — id, message_id, r2_key, file_hash (SHA-256), ipfs_cid (nullable, заполняется в Фазе 6), kind [handoff_photo, receipt_photo, doc, payment_receipt], created_at. **Иммутабельно.**

> [!IMPORTANT]
> `nostr_pubkey`, `category`, `business_activity_level`, `ipfs_cid` вводятся в Фазе 1 как nullable-заглушки — чтобы Фазы 2–6 добавляли логику без миграций моделей.

> [!NOTE]
> **IPFS-readiness:** `file_hash` (SHA-256) — это уже multihash-основа CID. Поле `ipfs_cid` в `Attachment` хранит CID после пина в Фазе 6. `DealVaultMessage` и `DealEvent` структурированы как сериализуемые Nostr-события: при добавлении подписи (Фаза 2) они становятся валидными Nostr event objects.

*Никакого UI до завершения и тестирования моделей.*

### 1.2 Аутентификация + Социальный граф
1. JWT-auth (регистрация/логин).
2. **InviteLink**: пользователь генерирует ссылку-приглашение (`/invite/{token}`); друг переходит, регистрируется (или логинится), связь создаётся автоматически.
3. **Connection**: двусторонняя связь между пользователями; видна в профиле как «Ваши контакты» — люди, с которыми уже проводились доставки или кого вы пригласили.
4. **Guest-invite**: сделка может создаваться с `recipient_contact`; по ссылке получатель регистрируется и привязывается к сделке.

### 1.3 Базовый API (маршруты и сделки)
- `POST /api/trips` — опубликовать рейс/маршрут поездки.
- `GET /api/trips` — список рейсов (с фильтрами: маршрут, дата, категория).
- `POST /api/deals/match` — сопоставить отправителя и рейс (создать сделку).
- `POST /api/deals/{id}/accept` — принять условия (→ accepted).
- `POST /api/deals/{id}/event` — зафиксировать событие (handoff/in_transit/received).
- `GET /api/deals/{id}/dealvault` — получить чат, фото и лог DealVault.
- `POST /api/deals/{id}/dealvault/messages` — сообщение/фото (загрузка в R2/S3, SHA-256, CID-заглушка).
- `POST /api/deals/{id}/confirm` — подтвердить получение (→ confirmed → closed).
- `GET /api/deals` — мои доставки.
- `POST /api/invites` — создать invite-ссылку.
- `POST /api/invites/{token}/accept` — принять приглашение (создать Connection).
- `GET /api/me/connections` — список связей в профиле.

## 5. Фаза 2 — Идентификация и ключи

> **Цель:** верифицированные силами сети участники, keypair как основа портативности. Regulatory KYC — Фаза 4. Зависимость: Фаза 1 стабильна.

### 2.1 Peer Identity Verification + Verification Levels (P2P KYC)
1. `VerificationLevel` enum: `auto` / `peer` / `kyc`.
2. `VerificationRequest` — id, deal_id, requested_by, `target_role ∈ {sender, carrier}`, status ∈ {pending, upload, later_in_person, declined, declined_polite, verified, escalated}.
3. `IdentityContainer` — id, owner_id, `owner_role ∈ {sender, carrier, both}`, `storage_mode ∈ {encrypted_blob, zk_snark}` (default encrypted_blob; zk_snark добавляется в T6.4), blob_encrypted BYTEA, doc_hash, doc_country, doc_type, sanctions_check_status. Ключ шифрования = owner's Nostr nsec (из T2.2). Multi-doc: один пользователь → много контейнеров. **Owner_role=carrier** — опция для перевозчика получить badge.
4. `VerificationBadge` — id, subject_id, level, source ∈ {auto_ocr, peer, arbiter_review, kyc_provider}, container_ref_id, verified_by_id?, in_deal_id?, verified_at, expires_at?, revoked_at?. Append-only.
5. **Три варианта ответа отправителя** (target=sender): `later_in_person` / `declined` (метка + возможность cancel) / `upload`.
6. **Три варианта ответа перевозчика** (target=carrier): `upload_now` / `later_in_person` / **`declined_polite`** — **без последствий**, в чате нейтрально-серое system-message «В целях собственной безопасности перевозчик решил не раскрывать своё имя. Отправитель вправе отменить сделку без штрафа.»
7. **Асимметрия обоснована**: перевозчик пересекает границы, его identity — оперативный риск; sender передаёт ценное, его identity — гарантия другой стороне.
8. Multi-doc по принципу US DMV — если сомнения → запрос второго документа.
9. Escalation при подозрении на фальшивку → создаётся `Dispute` из T1.23 с типом `identity_fraud`.
10. Локальный OCR: PaddleOCR (fallback tesseract) — без внешних API.
11. Санкционные списки: OFAC SDN + EU consolidated — публичные CSV, обновляются ежедневно.
12. **Trip.carrier_verification_level** денормализован — chip на карточке в TripsPage + фильтр `min_level`. Даёт бонус к УБА в Фазе 3 (`V_verify_factor`, множитель [1.0…1.3]).

### 2.1a Trust Graph (Web-of-Trust)
1. `TrustEdge` — id, from_user_id, to_user_id, kind ∈ {peer_verified, dealt_with, invited}, weight, source_ref.
2. Sybil-guard: `peer_verified` edge валиден только если между парой есть `DealStatus.closed`.
3. `GET /api/me/trust-circle?depth=N` — BFS до глубины 6.
4. Публичная метрика: `verifications_issued_count`, `verifications_received_count`.

### 2.2 Keypair + Nostr-совместимость (D10: Вариант A + D)
1. При регистрации генерируется secp256k1-keypair. `nsec` хранится зашифрованно (AES-256-GCM; ключ шифрования в env/KMS, не в БД). `npub` → `User.nostr_pubkey`.
2. `User.key_self_custody: bool = False` — флаг наличия nsec у платформы.
3. DealVault-события подписываются server-side: `sig = schnorr_sign(event_hash, nsec)`. Сервер верифицирует подпись по `npub` перед сохранением.
4. **Self-custody path:** `POST /api/me/keypair/export` (re-auth) → `POST /api/me/keypair/claim` → платформа удаляет nsec, `key_self_custody = True`; дальнейшая подпись — client-side или NIP-07.
5. **Import:** `POST /api/me/keypair/import` принимает существующий npub; платформа не хранит чужой nsec; `key_self_custody = True` сразу.
6. **NIP-07 (Вариант D):** frontend обнаруживает `window.nostr` → запрашивает `getPublicKey()` → предлагает переключиться на extension-подпись → frontend передаёт pre-signed event, сервер верифицирует. Extension-подпись имеет приоритет над custodial.

## 6. Фаза 3 — УБА и арбитраж

> **Цель:** метрика доверия и разрешение споров. Зависимость: Фаза 2 стабильна.

### 3.1 Уровень Бизнес-Активности (УБА)

Рассчитываемая метрика доверия. Заменяет заглушку `User.business_activity_level` Фазы 1.
Recalculate: Celery beat, каждый час; кеш в `User.business_activity_level`.

**Компоненты (скользящее окно: последние 90 дней)**

| Символ | Что измеряет | Источник данных |
|---|---|---|
| F — Частота | Завершённых рейсов в месяц | `Deal.status = closed`, деление на 3 |
| Q — Качество | Подтверждённых доставок с фото | `Deal` с DealVault-фото передачи + получения |
| V — Объём | Суммарная задекларированная стоимость (USD) | `SUM(Order.declared_value)` по closed deals |
| D — Депозит | Пиковый размер активного залога | `MAX(Collateral.amount)`; 0 если не использовался |
| **Vrf — Verification level** | Highest active `VerificationBadge.level` | `User.highest_verification_level` (T2.1) |

**Формула**

```
F_norm   = min(F / 8,   1.0)                              — насыщение при 8 рейсах/мес
Q_norm   = min(log₁₀(Q + 1) / log₁₀(51),  1.0)          — насыщение при 50 сделках
V_norm   = min(log₁₀(V + 1) / log₁₀(50001), 1.0)        — насыщение при $50 000

D_factor      = 1.0 + 0.5 × min(D / 5000, 1.0)          — диапазон [1.0 … 1.5]

V_verify_factor:                                          — бонус за уровень верификации
  null → 1.00 (нейтральный)
  auto → 1.05
  peer → 1.15
  kyc  → 1.30

# Нормализация чтобы max УБА оставался 1000:
V_verify_norm = V_verify_factor / 1.30                    — диапазон [~0.77 … 1.0]

УБА = round(F_norm × Q_norm × V_norm × D_factor × V_verify_norm × 1000)  — диапазон [0 … ~1000]
```

**Уровни**

| УБА | Уровень |
|---|---|
| 0–49 | Новичок |
| 50–199 | Проверенный |
| 200–449 | Надёжный |
| 450–749 | Доверенный |
| 750–1000 | Элита |

**Ключевые решения формулы**
- `D_factor` — множитель-бонус, не штраф. Без залога D = 0 → factor = 1.0 (нейтральный). Депозит усиливает УБА, но не уничтожает его при отсутствии.
- `Q` считает только сделки с **обоими** фото в DealVault (передача + получение). Без фото — не засчитывается.
- Логарифмическая шкала Q и V защищает от накрутки микро-сделками с низкой стоимостью.
- `F` — не просто количество рейсов, а активность текущего периода (rolling window).
- Видимость: профиль пользователя + карточка участника при мэтчинге.

### 3.2 Оператор-арбитр и споры
1. Роль `Operator`; консоль.
2. `Dispute` — id, deal_id, opened_by, status, verdict.
3. `OperatorAccessGrant` — доступ к DealVault конкретной сделки по запросу стороны.
4. Вердикт → при наличии эскроу (Фаза 5) направляет разблокировку через ключ арбитра.

## 6.5 Фаза 3.5 — Vimana Nostr Relay + Federation

> **Цель:** свой Nostr-relay в prod; каждый рейс = signed event в глобальной сети. Зависимость: Фаза 2 (keypair) + Фаза 3 (арбитраж, УБА).

### 3.5.1 Relay-runtime + event model
1. **strfry** как отдельный контейнер `nostr-relay` в docker-compose. LMDB storage, NIP-01/NIP-11/NIP-42/NIP-99.
2. Trip event model: **kind 30402** (NIP-99 Classified Listing, replaceable per `d`-tag). Tags: `d`, `l` (locations IATA), `t` (categories), `published_at`, `expires_at`, `capacity`.
3. Signed user's nsec (из T2.2) — не платформенным ключом.

### 3.5.2 Publish bridge

3. Идемпотентность через `Trip.nostr_event_id` (unique).

## 6.6 Фаза 3.6 — DealVault Protocol: полнота цепи + Identity-пересечение

> **Цель:** DealVault соответствует концепции «Verifiable Vault Protocol» — цепь покрывает всю историю сделки (не только статусы), закрытие запечатывает vault, identity-данные пересекаются между Identity Vault и Deal Vault. Публикация якорей остаётся выключенной (server-only), расширение заложено схемой. Зависимость: T3.6 (цепь), T2.1 (verification), T2.2 (подписи).

### 3.6.1 Полнота цепи
1. `DealEventType` += `message_added` / `file_added` / `sealed` / `identity_ref`; события пишутся через существующий `append_deal_event` в одной транзакции с контентом.
2. Хешируются хранимые байты (`sha256(ciphertext+nonce)`, `file_hash`) — верификация без расшифровки, E2E не нарушается.
3. Seal при закрытии сделки: финальное событие + запрет append.
4. `deal_chain_anchors.backend` (`nostr` | `ipfs` | `ots`) — расширяемость публикации без кода новых бэкендов.
5. Публичный для участников `GET /deals/{id}/vault/verify` с coverage-метриками.

### 3.6.2 Контент-валидация файлов

## 6.7 Фаза 3.7 — Идентичность и вход

> **Цель:** три способа входа поверх личности, которой **является сам Nostr-ключ**. Разделение уровней: **npub** — личность (создаётся один раз, при переходе в self-custody, дальше неизменна); **Passkey / Nostr-подпись / пароль** — способы входа (сменяемы, множественны); **JWT** — краткоживущая сессия (T_UX.3). YubiKey — не отдельный механизм, а WebAuthn-аутентификатор с аппаратной привязкой. Отдельная сущность DID не вводится: `nostr_pubkey` и есть идентификатор.
>
> **Философская позиция (решение владельца, 2026-07-26):** проект ближе к Nostr и Bitcoin — «ключ и есть личность». Отсюда два следствия. Первое: до перехода в self-custody личности **нет** — ключ, которым платформа шифрует сейф, служебный, и как личность пользователю не подаётся. Второе: смена или потеря ключа означает появление **новой личности**, а не восстановление старой; переход всегда даёт новый ключ, а не повышает служебный. Осознанный отказ от «неизменной личности при смене ключа» ценой необратимости утраты. Зависимость: T2.2 (custody-механика), T_UX.3 (сессии).

### 3.7.1 Email-only регистрация + подтверждение кодом
1. Телефон уходит из регистрации и логина; `User.phone` остаётся nullable-полем профиля.
2. 6-значный код, хранится хешем, TTL 15 мин, 5 попыток; отправка — Celery-таском (`send_email` синхронный).
3. Подтверждение **не гейтит ничего**: это безопасность, а не права. Неподтверждённый адрес ставит под вопрос канал восстановления доступа и уведомлений по сделкам — поднимает это UI, не API.

### 3.7.1a Лестница владения личностью (пересмотр 2026-08-01, `D-KEY-TIERS`)

> Пункты 3.7.2–3.7.5 ниже написаны под прежнюю бинарную модель и читаются **через** этот раздел: где они говорят «переход всегда даёт новый ключ» и «утрата ключа необратима» — действует `D-KEY-TIERS`.

Модель описывается вокруг личности, а не вокруг места хранения ключа. Четыре ступени, вверх — независимость, вниз — удобство:

| | Ступень | Пользовательский ключ | Кто подписывает | Что может платформа |
|---|---|---|---|---|
| 0 | Только аккаунт | нет | серверный ключ платформы | всё |
| 1 | Nostr-личность есть | только у платформы | платформа, от имени пользователя | всё |
| 2 | Копия у вас | у вас **и** у платформы | платформа, от имени пользователя | всё, но вы не заперты |
| 3 | Только ваш | только у вас | браузер (NIP-07 или ключ из файла) | хранит сделки, открыть не может |

1. Ступень 1 наступает **при регистрации**, отдельного действия не требует. Ступень 0 остаётся реальным состоянием только для приглашённых получателей (T3.3), которые в сервисе не регистрировались.
2. Ступень 2 — скачивание **Identity Vault** (`.dvlt`). Ключ запечатывается парольной фразой (NIP-49) **в браузере**; фраза на сервер не уходит и платформой не хранится. Фраза — не пароль от аккаунта и до первого скачивания не нужна.
3. Ступень 3 — удаление копии с платформы. Единственный необратимый шаг, единственный экран с последствиями.
4. Движение вниз: загрузка `.dvlt` + фраза возвращает копию на платформу. Потеря личности требует **двух** потерь сразу.
5. Быстрый путь: свою личность можно привязать сразу после регистрации. NIP-07 → мы ключа не видим, сразу ступень 3. Вставленный `nsec`/`ncryptsec` → распечатывается в браузере, копию платформе оставлять или нет решает пользователь (по умолчанию — нет). Импорт **чужого** ключа означает смену личности и перешифровку сейфов (механика T3.12).
6. Статус в профиле — три состояния одной строкой: «копия только у нас» → «копия у вас и у нас» → «копия только у вас».

### 3.7.2 Служебный ключ vs личность
1. Механика T2.2 сохраняется: keypair выдаётся при регистрации и шифрует сейф — но это **служебный ключ платформы**, а не личность. `key_self_custody` уже различает эти два состояния, новых колонок не нужно. `nostr_pubkey` → NOT NULL + UNIQUE после бэкфилла тем, у кого ключа нет (12 юзеров, арбитр, superuser — попутно чинится неработающий threshold, `api/threshold.py:40`).
2. Рейсы до перехода публикуются только под отдельным `PLATFORM_PUBLISH_NSEC` и только отобранные фильтром «интересных». Служебным ключом не публикуем: событие в relay'ях вечно, а служебный npub при переходе уничтожается.
3. Переход (`establish identity`) **всегда даёт новый ключ** — `claim` удаляется вместе с `import` и `export`. Ключ рождается в браузере либо приходит из NIP-07; сервер требует только доказательство владения, ветки для него неразличимы.
4. Перешифровка сейфов — envelope-схемой: session-ключи переупаковываются на новый npub, байты контента не меняются, поэтому цепь T3.6 и `verify_content` целы. `IdentityContainer` перешифровывается целиком — его `doc_hash` считается по plaintext.
5. Утрата ключа — терминальное состояние (`key_lost_at`): аккаунт read-only, публично помечен, обратного перехода нет.

### 3.7.3 Способы входа
1. **Email + пароль** — существующий путь, `password_hash` становится nullable.
2. **Nostr-подпись** — одноразовый challenge (Redis, TTL 300s) + NIP-98; проверка через существующие `compute_event_id` / `verify_event_id`.
3. **Passkey (WebAuthn)** — discoverable credentials, usernameless-вход; несколько устройств на одну личность; отвязка устройства не трогает npub.

### 3.7.4 Step-up re-auth
- Чувствительные операции (экспорт nsec, claim self-custody, declare-lost, отвязка passkey, смена email) требуют свежего подтверждения любым из трёх пруфов — механизм не зависит от способа входа.

### 3.7.5 Восстановление доступа и необратимость
1. Recovery-коды (10 одноразовых, хеши) возвращают **доступ, но не ключ**. До перехода терять нечего — восстанавливается всё. После: ключ жив → восстанавливается всё, npub тот же; ключ утрачен → чистый старт, история не переезжает.
2. Напоминания привязаны к событиям, не к таймеру: молчим при регистрации (собственного ключа ещё нет, риска нет), баннер при первой сделке для аккаунта без email, экран последствий перед переходом.
3. Переход не блокируется — экран с обязательным чекбоксом понимания, но решение за пользователем (суверенитет).

### Отложено осознанно (не входит в фазу)
- Social recovery через Trust Graph (guardians + threshold) — и отдельно: она всё равно не вернёт ключ, только подтвердит человека. Подписанная старым ключом ротация личности. WebAuthn attestation-проверка производителя. Passwordless-переход существующих парольных аккаунтов.

## 6.8 Фаза 3.8 — Контакты, каналы и оповещения

> **Цель:** свести вход в одно поле, а доставку кодов и оповещений — в один механизм. Пользователь вводит **почту или телефон**, выбирает канал кода, и этим же жестом получает канал для оповещений. Зависимость: Фаза 3.7 (способы входа), T1.7 (существующие каналы). Решение владельца 2026-08-06 — TECHSTATE `D-CONTACT-CHANNELS`.
>
> **Отмена решения №1 Фазы 3.7.** Телефон возвращается в auth-путь. Позиция при этом не меняется, а уточняется: телефон никогда не был кандидатом в личности и им не становится — личность остаётся npub, лестница владения `D-KEY-TIERS` не затронута, регистрация по телефону даёт ту же ступень 1, что и по почте. Из auth его убирали как «лишний идентификатор»; возвращается он как **подтверждаемый контакт и канал** — та же роль, что у почты, passkey и Nostr-подписи.

### 3.8.1 Один контакт — один механизм
1. Истина о контактах переезжает в `user_contacts(channel, value, verified_at, is_login)`; `users.email` / `users.phone` остаются денормализованным основным контактом (их читает половина кода, переписывать её ради схемы этот этап не будет).
2. Уникальность подтверждённого контакта — **частичным** индексом `WHERE verified_at IS NOT NULL`. Полный `UNIQUE` позволил бы неподтверждённой заявкой на чужой номер навсегда запереть настоящего владельца.
3. Машина кодов из T3.11 (TTL 15 мин, 5 попыток, хранение хешем, cooldown, сжигание кода при исчерпании) обобщается на все каналы, а не форкается под каждый.
4. Телефон нормализуется в E.164 проверенной библиотекой. Ненормализованный номер не является идентификатором: три записи одного номера — три строки, и `UNIQUE` этого не знает.

### 3.8.2 Вход и регистрация одним путём
1. Одно поле (почта или телефон) → выбор канала → код. Пароля в регистрации нет; `password_hash` nullable с T3.11, вход по паролю для существующих аккаунтов сохраняется.
2. `POST /auth/otp/request` отвечает **202 всегда** — разный ответ на существующий и несуществующий аккаунт превращает публичную форму входа в оракул перебора.
3. `display_name` спрашивается после верификации: до подтверждения контакта аккаунта нет.

### 3.8.3 Каналы за флагами
1. `core/channels/` с единым `send_code(channel, value, code, locale)`; какие каналы живые — переменные окружения, не код.
2. Приоритет каналов выбран по достижимости и срокам, а не по привычке: **email и Telegram доступны сегодня**, Telegram Gateway — дни, SMS и WhatsApp — недели внешних согласований (10DLC в США, Sender ID в ОАЭ, верификация бизнеса в Meta). Для коридора ОАЭ ↔ США SMS — самый дорогой и медленный канал из пяти, и ставить его первым значило бы отложить этап на месяц ради худшего варианта.
3. Антифрод обязателен **до** включения любого платного канала: публичный «отправить код» — это готовая схема SMS-pumping, и счёт приходит платформе.

### 3.8.4 Оповещения
1. Матрица «класс события × канал» вместо трёх булевых тумблеров; хранение JSONB + дефолты в коде.
2. Класс **«безопасность» неотключаем**. Правило уже действует де-факто (код подтверждения, использованный recovery-код, удаление копии ключа, завершение личности не смотрят на `notify_email`) — фаза записывает его явно, потому что незаписанное правило склонно отрасти обратно в настройку.
3. Локализация оповещений на шесть локалей + `users.locale`. Сегодня тексты только по-русски при UI на шести языках.

### Отложено осознанно (не входит в фазу)
- Тихие часы и дайджест. Web Push как пятый канал. `List-Unsubscribe` в письмах. Полный перенос `users.email`/`phone` в `user_contacts` с переписыванием всех читателей. Телефон как способ **восстановления** доступа (пересекается с recovery-кодами T3.16 — решать отдельно, не походя).

## 6.9 Фаза 3.9 — Протокол сделки в чате

> **Цель:** сделать чат сделки одновременно записью и пультом. Зависимость: Фаза 3.6 (полнота цепи) закрыта.
> **Почему до денег:** на этом протоколе стоят все три уровня прибыли (MASTERPLAN §4.1). Эскроу без зафиксированного договора нечего исполнять, а бизнесу нечего показывать своему клиенту.

### 3.9.1 Принцип

**Ничего не происходит мимо чата.** Каждое действие по сделке порождает карточку в DealVault; каждая карточка вызывается оттуда же. Статус сделки — производная от карточек, а не наоборот.

Это даёт три вещи одной механикой: единственный источник доказательств для арбитра, одинаковый вид у одинаковых по смыслу действий, и готовые к подписи Nostr-события.

### 3.9.2 Модель

`DealVaultMessage` расширяется типизацией. Существующее поле `is_system` остаётся признаком «не пользовательский текст», типизацию несут новые поля:

| Поле | Смысл |
|---|---|
| `card_kind` | тип карточки (enum, nullable; `NULL` = обычное сообщение) |
| `card_payload` | структурные и числовые поля, читаемые сервером (суммы, вес, перечисления). Чувствительный текст — не сюда, а в зашифрованный `text` |
| `card_state` | `pending` · `accepted` · `declined` · `expired` · `superseded` |
| `requires_ack_by` | роль, обязанная ответить (`sender` / `carrier` / `recipient` / `operator`) |
| `acked_by`, `acked_at` | кто и когда ответил |
| `supersedes` | ссылка на карточку, которую эта заменяет |

**Префиксный хак из T1.26 заменяется.** «Share my address» сейчас шлёт `is_system=true` с текстовым префиксом `📍 SHARED ADDRESS`, а фронт парсит строку. Переводится в `card_kind='address.shared'` — та же карточка, та же вёрстка, но тип в поле, а не в тексте.

### 3.9.3 Шифрование

Разделение обязательное, иначе протокол неисполним:

- **Конверт** (`card_kind`, `card_state`, `requires_ack_by`, `acked_by/at`, `supersedes`) — обычные колонки, читаются сервером. Без этого нельзя ни валидировать переход, ни построить напоминание, ни показать «ждём подтверждения».
- **`card_payload`** — тоже читается сервером, но несёт только **структурные и числовые** поля, которые сервер обязан проверять: суммы, вес, перечислимые способы, ссылки.
- **Чувствительное тело** — адреса, описание груза, свободный текст — остаётся в поле `text`, зашифрованном AES-256-GCM как сейчас. Для сделок с эскроу — threshold-E2E (T2.3) **с обязательной долей арбитра**: иначе спор нечем разрешить. Механика готова — `is_e2e`, `wrapped_shares`, `read_packages`.

> Разделение именно такое, а не «шифруем весь payload»: сервер, не умеющий прочитать сумму, не умеет и удержать с неё сбор.

### 3.9.4 Каталог карточек

**Группа 1 · Договор** — уровень 0, обязателен

**Условия диктует перевозчик, отправитель может предложить свои.** Базовые условия задаются полями при публикации рейса; отправитель открывает чат по конкретному рейсу (`TripInquiry`, T1.22 — механика уже есть) и предлагает встречные. Обе ветки сходятся в одну карточку.

| Карточка | Инициатор | Payload | Подтверждает | Эффект |
|---|---|---|---|---|
| `terms.proposed` | перевозчик (из полей рейса) или отправитель (в чате по рейсу) | что везём, вес и габариты, объявленная стоимость, цена и валюта, срок, способ оплаты | контрагент | — |
| `terms.countered` | контрагент | те же поля | инициатор | `supersedes` предыдущую |
| `terms.agreed` | система | снимок согласованных полей + нормализованный вид | — | `Deal.status → accepted` |
| `terms.declined` | контрагент | причина | — | — |
| `terms.amended` | любая сторона | дельта полей | обе стороны | новая версия, старая `superseded` |
| `terms.reconfirm_requested` | система | причина: рейс вылетел без передачи | обе стороны | сделка не идёт дальше без переподтверждения |

`terms.agreed` — **неизменяемый договор сделки**. На него ссылаются все последующие карточки; арбитр читает его первым.

**Фиксация сумм происходит не здесь, а при передаче груза** (`handoff.confirmed`, группа 3): тогда закрепляются стоимость услуги, размер залога, курс и версия параметров платформы. Передача обязана состояться **до `Trip.depart_at`**. Если время вылета наступило, а передачи не было, система порождает `terms.reconfirm_requested` — стороны переподтверждают условия под новый рейс либо расходятся. **Автоматического продления нет.**

**Нормализация к общему виду.** Любое предложение, с какой бы стороны оно ни пришло, приводится к сопоставимым единицам — иначе предложения по разным рейсам не сравнить:

| Поле | Откуда |
|---|---|
| Направление | коридор из `origin` → `destination` рейса, например `US → Europe` |
| Расстояние, км | считается по координатам городов из имеющегося датасета GeoNames (T1.16 / T1.26) — новой зависимости не нужно |
| Вес, кг | из предложения; при габаритном грузе — оплачиваемый вес по правилу потока C |
| Итоговая цена | из предложения |
| **Цена за кг** | производная |
| **Цена за км** | производная |

Производные поля считаются на сервере и входят в снимок `terms.agreed`. Они же дают сравнимость в выдаче и материал для метрик ценообразования.

**Требуется расширение `Trip`.** Сейчас модель несёт `origin`, `destination`, `depart_at`, `capacity`, `allowed_categories` — **ценовых полей нет вовсе**. Добавляются базовые условия перевозчика: цена за кг, минимальная цена сделки, валюта, требуемый уровень залога (уровень 1 или порог пула), допустимые способы передачи.

**Группа 2 · Логистика передачи** — уровень 0

| Карточка | Инициатор | Payload |
|---|---|---|
| `handover.conditions` | любая сторона | упаковка, вскрывать/не вскрывать при передаче, обязательная фотофиксация, температурный режим, хрупкость |
| `pickup.proposed` / `.confirmed` | стороны | способ (лично · локальная почта · курьер · постамат), адрес, дата, окно |
| `dropoff.proposed` / `.confirmed` | стороны | способ вручения (в руки · локальная почта · курьер · до востребования), адрес |
| `address.shared` | владелец адреса | адрес из профиля (перенос T1.26) |
| `route.note` | система | предупреждение по коридору (T_UX.2) |

**Группа 3 · Владение грузом** — уровень 0

| Карточка | Инициатор | Обязательное вложение | Подтверждает | Эффект |
|---|---|---|---|---|
| `handoff.declared` | отправитель | `handoff_photo` | перевозчик | `DealEvent.handoff` |

| `transit.update` | перевозчик | — | — | необязательная: вылет, прилёт, задержка, таможня |
| `delivery.declared` | перевозчик | `receipt_photo` | получатель | `DealEvent.received` |

**Группа 4 · Расчёты** — уровень 0 (наличные) и уровень 1 (эскроу)

| Карточка | Инициатор | Payload | Подтверждает | Эффект |
|---|---|---|---|---|
| `payment.method_agreed` | стороны | наличные · на платформе · эскроу | контрагент | — |
| `escrow.funded` | система | сумма, адрес, подтверждения сети | — | Фаза 5 |

`payment.confirmed` — подтверждение приёма средств получающей стороной. Без него сделка не закрывается даже при наличном расчёте: именно эта карточка отличает «сказал, что заплатил» от «подтвердил, что получил».

**Группа 7 · B2B** — уровень 3 (поток C)

| Карточка | Payload |
|---|---|
| `b2b.order_created` | номер заказа бизнеса, конечный получатель, оплачиваемый вес |
| `b2b.leg_domestic` | внутренняя нога: передача курьеру или локальной почте, трек-номер |
| `b2b.proof_of_delivery` | POD для бизнеса — экспортируемый пакет для его клиента |

### 3.9.5 Инварианты протокола

1. **Статус — производная от карточек.** Прямая смена `Deal.status` вне карточки запрещена.
2. **Односторонних переходов нет.** Каждая `declared` требует `confirmed` от контрагента.
3. **Таймаут не подтверждает.** У pending-карточки есть срок; истечение даёт `expired` и эскалацию в напоминание (каналы Фазы 3.8), но **никогда не автоподтверждение**.
4. **Карточка неизменяема.** Правка = новая карточка со ссылкой `supersedes`.
5. **Всё идёт в цепь.** Карточка — это сообщение, значит уже покрыта `DealEventType.message_added` и якорями Фазы 3.6.
6. **Роли проверяются на сервере.** `requires_ack_by` — не подсказка фронту, а условие принятия ответа.

## 7. Фаза 4 — Карточные платежи + Regulatory KYC

> **Цель:** монетизация без крипты. Появление реальных денег → появление regulator'а. Зависимость: Фаза 3.5 стабильна.

### 4.1 Классический regulatory KYC / AML
1. Выбор провайдера — TECHSTATE Decision Log D-KYC (варианты: Sumsub / Onfido / Jumio).
2. `KycRecord` — id, user_id, provider, external_id, status ∈ {pending, verified, rejected, expired}, verified_at, expires_at, level.
3. `ComplianceAck` — id, user_id, doc_version, category, acknowledged_at.
4. Webhook провайдера → обновляет `KycRecord.status` → триггерит evaluation прав.
5. Permission `PLATFORM_PAYMENT_INITIATE` требует `KycRecord.status = verified`.
6. **Corridor-периметр НЕ блокируем.** Информационная задача `T_UX.2 Route notes + platform disclaimers` (cross-cutting) — платформа показывает статус коридора (standard / attention / complex / restricted) с i18n-текстом, но не запрещает публикацию/матч. Позиция зафиксирована в TECHSTATE `D-COMPLIANCE-STANCE`.

### 4.2 Платежи на платформе
1. `Payment` — id, deal_id, method [card], amount, platform_fee, status.
2. Интеграция карточного процессинга. Комиссия платформы с каждой транзакции.
3. Все платёжные события пишутся в `DealEvent`.
4. **Зависит от T4.1** — пользователь без verified KYC → 403.

## 8. Фаза 5 — Крипто-эскроу

> **Цель:** доверие к деньгам для дорогих грузов. Зависимость: Фаза 4 стабильна.

### 5.1 Эскроу BTC + Залог (HodlHodl-схема)

> Техническая спецификация схемы (скрипт, деривация ключей, валидация эскроу, PSBT, модель угроз, отличия для Vimana): **`hodlBTCescrow.md`**.
> Там же §13 — замер экономики эталона по блокчейну.
> Модель монетизации, в которую встроен этот блок: **MASTERPLAN §4.1**.

1. `Escrow` — id, deal_id, chain [BTC], type [multisig_2of3], lock_address, amount, arbiter_pubkey_ref, status [created, funded, released, refunded, disputed].
2. `Collateral` — **постоянный залог перевозчика, не привязанный к сделке**: carrier_id, asset [BTC, USDT], custody_mode [custodial, non_custodial], amount, lock_address, timelock_until, status. Одна запись на перевозчика, а не на сделку. Уровень доступа (0 / 1 / пул магазина) и допустимая экспозиция — производные от неё, MASTERPLAN §4.1.
3. Схема **2-of-3 multisig**: ключи — плательщик, перевозчик, **платформа (арбитр)**; релиз — 2 подписи; платформа подписывает **только при споре**. **Средства не кастодируются платформой.**
4. Некастодиальный кошелёк на платформе для возвратов.
5. **Фи за эскроу — поток A из трёх (MASTERPLAN §4.1).** Процент берётся от **объявленной стоимости груза**, не от вознаграждения перевозчику. Шкала **предельная** (по частям суммы, как подоходный налог), нижний порог **$400**, документы — по нижнему порогу независимо от рыночной стоимости: 5 % от $400 до $2 000, 3 % от $2 000 до $10 000, 2 % свыше. Комиссия со сделки как таковой не берётся — мэтчинг бесплатен.
6. **Залог кладёт только перевозчик, и он постоянный.** Три уровня доступа (без залога / с залогом / пул магазина) и формула `допустимая экспозиция = залог × множитель верификации` — MASTERPLAN §4.1. Экспозиция считается по сумме объявленных стоимостей **грузов в пути одновременно**, значит нужен счётчик занятой экспозиции и его освобождение при закрытии сделки. Размер залога и уровень доступа — **публичные атрибуты перевозчика, видимые отправителю до мэтчинга**.
7. **Подтаивание залога — способ собрать поток A при расчёте вне платформы.** Одна закрытая сделка — один сбор: при расчёте через эскроу удерживается на релизе и залог не трогается; при наличном расчёте списывается с залога; у перевозчиков без залога сбора нет. Нужны идемпотентность списания (двойное списание за одну сделку недопустимо) и блокировка новых сделок при экспозиции ниже требуемой.
8. **Некастодиальный режим залога — опция, а не режим по умолчанию.** Кастодиальный: кошелёк платформы, списание автоматическое. Некастодиальный: **2-of-2 мультисиг перевозчик + платформа с таймлок-выходом перевозчика в одиночку**, списание подписывается перевозчиком в том же жесте, что и закрытие сделки. Таймлок обязателен — без него перевозчик не заберёт средства при исчезновении платформы. Для USDT некастодиальный режим — контракт-хранилище в поддерживающей сети, отдельная реализация.
9. **Комиссия за эскроу в B2B не начисляется** — включена в цену за килограмм (поток C, MASTERPLAN §4.1); поток A тарифицирует только C2C.
7. **Graceful degradation:** при недоступности крипто-слоя сделки Фаз 1–4 продолжают работать.

### 5.1a Параметры бизнес-логики в админке

Проверено в коде 2026-08-16: админ-панель есть (`api/admin.py`, страницы Vault / Disputes / Users / Email / Notices), роль в `users.role`, права — `core/permissions`. **Модели настроек нет: все ставки и пороги сегодня живут константами в коде.** Это терпимо, пока их три, и нетерпимо теперь.

1. `PlatformParameter` — **версионируемая** запись: ключ, **область действия** (`global` или конкретный коридор), значение, тип, `effective_from`, кто и когда изменил, комментарий. Изменение не правит строку, а создаёт новую версию.
2. Страница управления в существующей админке — **новая страница по образцу имеющихся**, а не новая панель.
3. Под управление выносятся: сбор с перевозчика (3 % от стоимости услуги) · множители экспозиции (×1 / ×2 / ×4) · шкала 5 / 3 / 2 % и её пороги · нижний порог $400 · **минимальный залог — задаётся по коридорам, не глобально** · типовой порог пула магазина · доля платформы в потоке C (18,9 %) · делитель объёмного веса · цена премиума.
4. **Изменение параметра не действует задним числом.** Версия параметров фиксируется при передаче груза (`handoff.confirmed`) и записывается в сделку; новая версия применяется только к передачам после `effective_from`.
5. **Коридорная область — не украшение.** Минимальный залог на ОАЭ ↔ США и на внутриевропейском маршруте не может быть одним числом: разные стоимости грузов, разные риски, разная плотность перевозчиков.
5. Аудит обязателен: кто, когда, что и с какого на какое значение. Ставка — это деньги пользователей, тихая правка недопустима.

## 9. Фаза 6 — Премиум + IPFS-портативность

> **Цель:** доп. ценность и полная децентрализация данных. Зависимость: Фаза 5 стабильна.

### 6.1 Премиум
- `PremiumSubscription`; хранилище документов + учёт (история, экспорт отчётов).

### 6.2 DealVault → IPFS
- Для каждого `Attachment`: SHA-256 → multihash → CID; файл пинится в IPFS (или Filecoin/Pinata); `Attachment.ipfs_cid` заполняется.
- Для каждого `DealVaultMessage`: сериализуется как Nostr event JSON (signed keypair из Фазы 2), пинится в IPFS; CID сохраняется.
- Полный DealVault сделки экспортируется как self-contained IPFS DAG: CID корня = верификационный хеш всей записи.

### 6.3 Полная Nostr + IPFS портативность
- Экспорт отвязываемого пакета аккаунта: профиль, все DealVault как Nostr-события, IPFS CID вложений.
- Аккаунт совместим с Nostr-клиентами: npub идентифицирует пользователя, прошлые записи верифицируемы.
- Решение по операторской/админ-панели — зафиксировать в Decision Log TECHSTATE.

### ✅ Phase 6 Integrity Check
- [ ] CID каждого вложения совпадает с SHA-256 при верификации?
- [ ] DealVault-экспорт самодостаточен без платформы?
- [ ] Nostr-совместимость: npub → все signed events проверяемы?
- [ ] Премиум не даёт нечестного преимущества в УБА?

## 9.5 Фаза 7 — Агентский доступ по сети

**Заведена 2026-07-30, не по плану, а по факту находки.** `mcp-server` одиннадцать дней перезапускался по кругу: `server.py` работает по транспорту stdio, при котором клиент сам запускает сервер дочерним процессом. Как сервис в compose он получал закрытый stdin, выходил с кодом 0 и поднимался снова.

Отсюда вскрылось расхождение с `D-AGENTIC-INTERFACE`, который обещает MCP-сервер контейнером для внешних клиентов: **с stdio это недостижимо в принципе**, а не сложно — снаружи до stdin процесса нет пути.

Фаза содержит одно решение и его последствия: **T7.1** — либо перевод на сетевой транспорт (streamable HTTP за nginx, с переносом rate-limit в Redis и ключа из аргумента tool'а в заголовок), либо признание, что сервер запускается клиентом локально и контейнер не нужен. Взвесить стоит с учётом того, что рейсы уже публикуются в Nostr (kind 30402) — канал обнаружения для агентов существует и работает без MCP.

Почему отдельной фазой, а не cross-cutting задачей: это не доработка, а пересмотр принятого решения об архитектуре внешнего доступа. Сетевой вариант заводит новую публичную поверхность, и её место — после Фазы 6, а не между делом.

## 9.6 Фаза 8 — DealVault на Pubky: распределённые сейфы и социальное восстановление

> **Первая фаза после выхода Альфа 1.** Зависимость: релиз состоялся, фазы 1–7 закрыты.
> Инженерная спецификация целиком — **`DealVault_architecture.md`** (артефакт, не дублируется здесь). Ниже — порядок работ и то, что нельзя потерять при переносе.

### 8.0 Что именно меняется

Пять уровней вместо нынешней монолитной модели: **Identity** (ключевая пара, эпохи ключа) → **Discovery** (Pkarr/Mainline DHT ищет Homeservers) → **Storage** (Homeserver хранит непрозрачные шифротексты) → **Vault** (сейф сделки со своим ключом) → **Recovery** (threshold-авторизация новой эпохи ключа).

Формула, задающая границы ответственности:
`DHT = discovery · Homeserver = недоверенное хранилище · Identity key = полномочия · Vault key = конфиденциальность · Guardians = право на восстановление`

### 8.1 Порядок реализации

Десять шагов из `DealVault_architecture.md` §«Порядок реализации», каждый становится задачей `T8.x` в TASKS: подключение Pubky SDK и identity → сейф как namespace зашифрованных объектов → ключи сейфов и конверты по участникам → Identity Vault и реестр → распределение и восстановление копий → отношения с гардианами → `3-of-5` и эпохи ключа → задержка, отзыв, аварийный сценарий компрометации → threat modeling и анализ утечки метаданных → только после этого production.

**Порядок не переставляется.** Гардианы (шаг 6) бессмысленны без реестра сейфов (шаг 4): восстанавливать нечего, если после смены ключа неизвестно, где лежат сейфы и какими ключами они открываются.

### 8.2 Что переиспользуется, а что пишется

Из Pubky SDK берутся публичные ключи, подписи, аутентификация, разрешение Homeserver, операции хранения, Pkarr-discovery и event streams. **Не считать уже готовым** в Pubky: полноценный `/priv`, сквозное шифрование общего назначения и автоматическое зеркалирование между Homeservers — если DealVault это нужно, это пишется нами.

Поверх SDK пишется всё, что перечислено в спецификации §«Что реализовать поверх Pubky» — от модели данных сейфа до аварийного сценария при компрометации ключа.

**Криптографические примитивы не изобретаются.** Выбор подписи, согласования ключей, KDF, AEAD, хеша, CSPRNG и threshold-схемы — отдельное архитектурное решение со своей threat model, фиксируется в Decision Log до первой строки кода.

### 8.3 Пересечение с тем, что уже построено

- **`D-KEY-TIERS` не отменяется, а получает верхнюю ступень.** Сегодняшние четыре ступени описывают, у кого копия ключа. Фаза 8 добавляет ответ на вопрос, что делать, когда копий не осталось ни у кого, — и тем самым снимает терминальность `key_lost_at` (`D-RETIRED-IS-ARCHIVE`), которая сейчас необратима by design.
- **Social recovery перестаёт быть отложенной.** В §6.7 «Отложено осознанно» она названа с оговоркой «всё равно не вернёт ключ, только подтвердит человека» — Фаза 8 принимает эту оговорку как **устройство механизма**, а не как возражение против него: ключ и не возвращается, авторизуется переход на новый.
- **Цепь и якоря (T3.6/T3.20) остаются.** Они доказывают целостность записи, Pubky отвечает за то, где она лежит и кто может её открыть, — это разные утверждения, и одно не заменяет другое.

### ✅ Phase 8 Integrity Check
- [ ] Новое устройство с `K0` разворачивает все доступные данные по цепочке `PK0 → DHT → Homeservers → Identity Vault → Deal Vaults`?
- [ ] Недоступность одного Homeserver не делает сейф недоступным при наличии копии на другом?
- [ ] Компрометация одного Homeserver не даёт ключей ни к одному сейфу?
- [ ] Гардианов меньше порога — личность не восстанавливается?
- [ ] Поддельная DHT-запись отклоняется по проверке подписи, эпохи и срока?
- [ ] Старый recovery-запрос или сертификат нельзя переиграть и откатить эпоху?
- [ ] Владелец с живым `K0` может отменить начатое восстановление до истечения задержки?
- [ ] Ротация `K0 → K1` не требует перешифровки существующих документов, и старые Vault Keys остаются доступны?
- [ ] Ни один путь хранения не содержит читаемого имени сделки, участника или суммы — только непрозрачные идентификаторы?
- [ ] В интерфейсе и в текстах нигде не сказано, что восстановление возвращает **ключ**, и нигде не обещано устранение утечки метаданных?

## 10. Что сознательно откладываем (за пределами 6 фаз)
- Эквайринг банковских API сверх базового процессинга.
- Интеграция с таможенными/судебными системами.
- Многосторонние сделки (только 1-на-1 + получатель).
- Нативное мобильное приложение (начинаем с web).
- **Multi-device для self-custody E2E** (сделка открыта на десктопе, продолжена на мобильном). Custodial-пользователи работают с любого устройства уже сейчас (`/decrypt-for-me` device-agnostic). Для self-custody: приоритет — NIP-46 remote signing (чисто фронтенд, ключ не копируется); задел — per-device envelopes: `read_packages` (JSON-map) расширяется ключами `sender_device_<id>` без миграций. НЕ роль и НЕ новый DealParticipant — устройство это «где живёт ключ», а не «кто».
